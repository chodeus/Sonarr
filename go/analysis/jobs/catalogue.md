# Jobs catalogue

This is a flattened porter-checklist of every periodically-running, event-driven, or user-invoked unit of work in the Sonarr v5 backend. It is synthesized from `subsystems/system.md` (the cross-cutting card that already drafts the scheduler, housekeepers, and health checks) plus per-row verification against `src/NzbDrone.Core/{Jobs,Housekeeping,HealthCheck,...}/**`. Cross-references to other cards (`messaging.md`, `decisionengine.md`, `indexersearch.md`, `download.md`, `mediafiles.md`) are kept short — the master cards retain the behavioural narrative.

In Sonarr a **command** (`abstract class Command` at `src/NzbDrone.Core/Messaging/Commands/Command.cs:8`, handled by `IExecute<TCommand>` at `src/NzbDrone.Core/Messaging/Commands/IExecute.cs`) is a single unit of work pushed onto an in-memory queue and executed one-at-a-time on a worker pool (see `messaging.md` for the bus). Commands carry virtual properties — `SendUpdatesToClient`, `UpdateScheduledTask`, `RequiresDiskAccess`, `IsExclusive`, `IsLongRunning`, `CompletionMessage` — that the executor honours. Commands originate from three places: (a) the **scheduler** (`Jobs/TaskManager.cs` + `Jobs/Scheduler.cs`) that wakes 11 default tasks on per-task intervals; (b) **the API / SignalR bus** when a user clicks "search now", "rename", etc.; and (c) **other commands or handlers** that re-emit a follow-up command (e.g. `ApplicationUpdateCheckCommand` enqueues `ApplicationUpdateCommand` if a new build is available).

A **housekeeper** (`IHousekeepingTask` at `src/NzbDrone.Core/Housekeeping/IHousekeepingTask.cs:3`) is a once-a-day cleanup unit registered alongside the daily `HousekeepingCommand`; the service iterates every registered task, swallows per-task exceptions, then `VACUUM`s the main DB regardless. A **health check** (`IProvideHealthCheck` at `src/NzbDrone.Core/HealthCheck/IProvideHealthCheck.cs:3`) is a self-diagnostic that runs on startup, on the 6-hourly `CheckHealthCommand`, and/or on specific events via `[CheckOn(typeof(SomeEvent))]`. Commands, housekeepers, and health checks are different abstractions but all flow through the command/event bus and are wired in `NzbDrone.Core/Composition`. This catalogue is the porter's Phase 3 checklist — every row needs a Go equivalent or an explicit "drop in port" decision.

Counts (verified against C# tree on 2026-05-02):
- **Commands with `IExecute<T>` handlers: 36** (including `TestCommand`/`UnknownCommand` which are infra-internal, and the 5 search commands cross-cited from `indexersearch.md`).
- **Default scheduled commands: 11** (per `Jobs/TaskManager.cs:67-135`).
- **Housekeepers: 31** (32 .cs files in `Housekeeping/Housekeepers/` minus 1 abstract base `FixFutureProviderStatusTimes`).
- **Health checks: 27** (26 in `HealthCheck/Checks/` + 1 `ServerSideNotificationService` in `HealthCheck/`).

## Open questions

- **JOB-Q1** unresolved — `DeleteBadMediaCovers` is a one-shot fix for a 2014-vintage bug; per `system.md` HOUSE-Q3 the Go port should drop it entirely. Cross-cite `system.md` HOUSE-Q3. Phase 3 (housekeeper port).
- **JOB-Q2** unresolved — Hard-coded interval/priority for each scheduled task in `TaskManager.Handle(ApplicationStartedEvent)` (`Jobs/TaskManager.cs:67-135`) means adding a new periodic command is a `TaskManager.cs` edit. Should the Go port move to a registration-by-attribute pattern (e.g. `[Schedule(Minutes = 720, Priority = Low)]` on the command type)? Cross-cite `system.md` JOBS-Q2. Phase 3 (scheduler port).
- **JOB-Q3** unresolved — `ImportListSyncCommand` interval is **5 minutes** — extremely aggressive given typical providers (Trakt list, Plex watchlist). Honor as-is in Go port, or expose `ImportListSyncInterval` config? Cross-cite `system.md` JOBS-Q1. Phase 3.
- **JOB-Q4** unresolved — 5 search commands (`EpisodeSearchCommand`, `MissingEpisodeSearchCommand`, `CutoffUnmetEpisodeSearchCommand`, `SeasonSearchCommand`, `SeriesSearchCommand`) all funnel into `ISearchForReleases` but are dispatched on three different services (`EpisodeSearchService`, `SeasonSearchService`, `SeriesSearchService`). Should the Go port collapse to a single dispatcher? Cross-cite `indexersearch.md` IS-Q* (all 12 of them). Phase 3 (search port).
- **JOB-Q5** unresolved — `IsExclusive` is honoured queue-wide (`HousekeepingCommand`, `ApplicationUpdateCommand`) but Sonarr's queue is in-memory only. With process restarts, exclusivity is best-effort. Should the Go port persist queue state to allow cross-restart exclusivity? Cross-cite `messaging.md`. Phase 3 (command bus port).
- **JOB-Q6** unresolved — `RescanSeriesCommand`, `RenameFilesCommand`, `RenameSeriesCommand`, `MoveSeriesCommand`, `BulkMoveSeriesCommand`, `DeleteSeriesFilesCommand`, `DownloadedEpisodesScanCommand`, `ManualImportCommand`, `ProcessMonitoredDownloadsCommand` all set `RequiresDiskAccess = true`. Sonarr does not currently *act* on this flag (it's metadata for the scheduler / UI gating). Should the Go port treat `RequiresDiskAccess` as a serialization key (so multiple disk-access commands don't run concurrently and trash each other's work-in-progress)? Phase 3.
- **JOB-Q7** unresolved — `IsLongRunning` flag is purely informational in C# (never read by the executor). Drop in Go port, or wire to a UI hint that pauses re-poll while the command runs? Phase 3.
- **JOB-Q8** unresolved — `UnknownCommand` / `UnknownCommandExecutor` is the fallback for command names whose handler was removed. Currently logs and discards. If the port renames any commands, the migration story for queued-but-not-yet-executed commands across upgrade is "they get discarded". Acceptable? Document in CONVERSION.md. Phase 3.
- **JOB-Q9** unresolved — `TestCommand` is wired in production DI (`TestCommandExecutor`) but is only exercised by integration tests. Drop the production registration in Go port, or keep the probe? Cross-cite `messaging.md`. Phase 3.
- **JOB-Q10** unresolved — `ResetQualityDefinitionsCommand` and `ResetApiKeyCommand` are destructive — there's no confirmation step; if the API endpoint is hit, the action runs immediately. Should the Go port require an `idempotencyKey` or `confirm: true` parameter for destructive commands? Phase 3 (cross-ref `sonarr-http.md`).
- **JOB-Q11** unresolved — Health-check `[CheckOn]` reflection-based dispatch is a custom layer over `IEventAggregator`. The Go port could (a) replicate via reflection, (b) require each check to register subscriptions explicitly in code, or (c) auto-generate subscription code from struct tags. Cross-cite `system.md` HEALTH-Q1. Phase 3 (healthcheck port).
- **JOB-Q12** unresolved — Housekeeping run-order is non-deterministic (assembly-scan registration order). With per-task try/catch, this rarely matters — but `CleanupOrphanedEpisodes` running before `CleanupOrphanedEpisodeFiles` produces a different orphan set than the reverse. Document explicit run-order in Go port. Phase 3.
- **JOB-Q13** unresolved — Housekeeping `Vacuum()` runs unconditionally after every batch. For large DBs (Sonarr installs with 100k+ episodes) this is multi-second. Gate on a "rows deleted > threshold" signal? Cross-cite `system.md` HOUSE-Q6. Phase 3.
- **JOB-Q14** unresolved — `ScheduledTask.LastStartTime` is written when the command starts; `LastExecution` is written when it completes. If the host crashes mid-command, `LastStartTime > LastExecution` persists; `FixFutureRunScheduledTasks` does NOT correct this. The next scheduler tick sees "interval elapsed since `LastExecution`" and fires again. Race window is short, but worth noting for the Go port. Phase 3.
- **JOB-Q15** unresolved — All `IExecute<T>` handlers in `IndexerSearch` and `Tv` services use `.GetAwaiter().GetResult()` to bridge sync `IExecute` against async-internal logic (`indexersearch.md` § Call graph). The Go port can make handlers natively async — pick the goroutine-per-command vs. worker-pool model. Cross-cite `messaging.md`. Phase 3.
- **JOB-Q16** unresolved — Three commands (`RestartCommand`, `ShutdownCommand`, `ApplicationUpdateCommand`) tear the host down. The current architecture relies on `IRuntimeInfo.RestartPending` + `ApplicationShutdownRequested` event. The Go port has no equivalent yet — pick `signal.NotifyContext` + a top-level `context.Cancel()`? Cross-cite `system.md` LIFE-Q1/Q2. Phase 3.
