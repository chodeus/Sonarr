# Sonarr Go-Port — Test Quality Audit

**Audit date:** 2026-05-20
**Author:** External review session (separate from the porting session that maintains `STATUS.md`)
**Question asked:** *"How can I be sure these tests aren't built to accept bad code or a bad port?"*

**Note to the porting Claude session:** This is a one-shot audit snapshot, not a tracking doc. Findings here can be folded into `STATUS.md` / `PHASE_5_AUDIT.md` / `PHASE_6_SCOPE.md` as appropriate. Feel free to delete this file once the actionable items are absorbed into the project's own planning docs.

---

## TL;DR

The contract harness is **architecturally correct and uses real C# data**, but it is **not engaged in CI** — every PR currently passes without ever asking the C#-recorded goldens whether the Go responses match. Unit tests are mixed but mostly real; the bigger structural risk is the unimplemented surface (write endpoints, stub providers) rather than tautological assertions.

Three concrete actions, ordered by leverage:

1. Wire `test/contract/replayer` into the CI workflow (it has goldens checked in; no live C# binary needed).
2. Run mutation testing (`gremlins` or `go-mutesting`) against `internal/parser`, `internal/customformats`, `internal/decisionengine`.
3. Stop using the 88% byte-equal headline as project completeness — it is read-side only.

---

## 1. Golden file provenance — AUTHENTIC

Sampled goldens at `test/contract/golden/v3-empty-state/v3.blocklist.golden.json:20-29` show:

- `Server: Kestrel` — ASP.NET Core's HTTP server. Go's `net/http` does not produce this header.
- `X-Application-Version: 10.0.0.26712` — a real C# Sonarr build identifier.
- `X-Miniprofiler-Ids: [...]` — .NET MiniProfiler instrumentation. Cannot be generated by Go.
- `Pragma: no-cache` + `Expires: -1` — classic ASP.NET cache-control pattern.

83 golden files exist across `host-bootstrap/`, `v3-empty-state/`, `v5-empty-state/`. All recorded against C# Sonarr 10.0.0.26712 via the `test/contract/recorder` CLI documented in `test/contract/README.md`.

**Verdict:** assertions are anchored to bytes a real C# binary produced, not regenerated from the Go port. Provenance is sound.

## 2. Contract replayer skips silently — HIGH RISK

`test/contract/replayer/replayer.go:44-48`:

```go
func Replay(t *testing.T) {
    t.Helper()
    if *flagBase == "" || *flagAPIKey == "" {
        t.Skip("contract.base and contract.api-key not set; skipping replay")
    }
```

The replayer is `t.Skip()`-gated on `-contract.base` and `-contract.api-key`. CI does not pass these flags (see §3), so the replayer skips on every CI run.

There is a guard test (`replayer_test.go:10-17` — `TestReplaySkipsWhenUnconfigured`) that verifies the skip behavior, so the skip is intentional. The consequence is that **`go test ./...` produces a green tree whether or not the contract suite actually ran.**

## 3. CI workflow — exists but does not run contract tests

`Sonarr/.github/workflows/build_go.yml:53-54`:

```yaml
- name: go test
  run: go test -race -count=1 ./...
```

No `-contract.base` or `-contract.api-key`. No step boots the Go binary. No step records goldens against a live C# binary.

The workflow IS triggered on push to `v5-develop` / `v5-main` and PRs to `v5-develop`. It runs `go vet`, `golangci-lint`, `go test ./...`, and cross-compiles binaries. The 83 contract goldens contribute zero enforcement on PRs.

**Fix sketch:** add a CI step that builds the Go binary, runs it on a known port against an empty SQLite DB, waits for `/ping` to return 200, then runs:

```sh
go test ./test/contract/replayer/... \
    -contract.base=http://127.0.0.1:8989 \
    -contract.api-key=$TEST_API_KEY \
    -contract.golden=./test/contract/golden \
    -contract.corpus=./test/contract/corpus
```

The goldens are checked in, so no live C# Sonarr is needed at CI time.

## 4. Unit test assertion quality — bimodal, mostly OK

**Verified-rigorous examples:**

- `internal/parser/enum_parse_test.go` — table-driven, direct value comparisons (`if got != tc.want`), covers empty / unknown / multi-value cases.
- `internal/episodefiles/queries_test.go:40-100` — explicit length checks, identity assertions on returned slices after CRUD, null-handling verified.
- `internal/importlistitems/importlistitems_test.go:69-90` — inserts then reads back via `repo.Get`, asserts every field round-trips, verifies nullables stay nil for sparse rows. Rigorous.

**Verified-weaker patterns (sampled, not exhaustive):**

- `internal/customformats/marshal_test.go:33-52` — asserts type cast succeeds and one field (`Name == "HDTV"`), does not verify other unmarshalled fields populated correctly.
- Several CRUD packages have early-test setup that uses `t.Fatalf` on insert errors without follow-up assertions. In most cases the file does have round-trip assertions later, but not all. Worth a sweep, not a panic.

**Verdict:** floor is higher than "tests pass if nothing panics." Some marshal/CRUD coverage is shallow on field-by-field verification. Mutation testing would surface these precisely.

## 6. The bigger risk: unimplemented surface (per PHASE_5_AUDIT.md)

The project's own Phase 5 audit (which I trust as authoritative for project state, since the porting session maintains it) documents:

- **45/51 GET endpoints byte-equal (88%).** This is the headline.
- **Zero write endpoints implemented** — every `POST` / `PUT` / `DELETE` under `/api/v3` is absent.
- **25 of 75 providers are schema-only stubs.**
- **Error response shape drift:** Go returns `text/plain`, C# returns a JSON envelope. Third-party clients that parse error bodies will break.
- **Handler-side logging is zero** — 500-class errors do not appear in logs.

Implication for the original question: **the tests cannot be tautological about behavior that doesn't exist yet.** The risk in this codebase isn't "tests give false confidence about correct code" — it's "the read-side that IS tested is well-tested, while the write-side that isn't yet implemented has no tests either, and a single percent-complete number lumps them together."

## Recommended verification actions (in order)

### A. Engage the contract suite in CI (highest leverage)

Add a job to `build_go.yml` that runs the replayer against the Go binary. Estimated effort: a few hours. Effect: every PR that changes a read-handler response is checked byte-for-byte against the recorded C# bytes. This converts an existing-but-dormant safety net into an active one.

### B. Mutation testing on parser-heavy packages

```sh
go install github.com/go-gremlins/gremlins/cmd/gremlins@latest
gremlins unleash ./internal/parser
gremlins unleash ./internal/customformats
gremlins unleash ./internal/decisionengine
```

Surviving mutants pinpoint assertions that don't actually constrain behavior. Skip the untested packages above — write tests for them first.

### C. Differential testing against a live C# Sonarr (longer-term)

Stand up the C# binary on port 8989 and the Go binary on port 8990, replay the same corpus against both via the `test/contract/diff` CLI in Mode B (documented in `test/contract/README.md:69-76`). This catches drift the goldens can't anticipate — locale, ordering quirks, error-path bodies.

### D. Audit a sample of marshal/CRUD tests for assertion density

Pick ~10 random `_test.go` files under `internal/`, read each end-to-end, and rate whether every meaningful return value is asserted. Mutation testing (B) catches most of these mechanically, but a human/agent read catches things like "the test exercises 200 lines and only asserts one field" that mutation testing rates as "covered."

### E. Separate the read-side completeness number from write-side

Wherever the project tracks completion, distinguish "read-side byte-equal coverage" from "write-side implementation." A consumer of the Go port sees zero benefit from 88% GET coverage if the write endpoints they depend on return 404.

## What was NOT done (scope notes)

- No `go test`, `gremlins`, or any state-mutating run — audit was read-only.
- No edits to source, tests, or project docs inside `go/`.
- No call-out of specific test files for rewrite — the floor is high enough that broad rewrite isn't warranted; targeted mutation-testing-driven fixes are the right move.
